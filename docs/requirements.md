## 1. 背景与目标

### 1.1 背景

日常开销分散在微信、支付宝、银行卡、现金等多个渠道，缺少一个统一、方便、可以随手记录的入口。月底想了解钱花在哪里时，往往需要翻账单或在表格里手工整理，过程繁琐且容易遗漏。

本产品面向个人及小型家庭场景，提供手机端记账工具，核心价值是“随手记录、按月看清、量入为出”。

### 1.2 产品目标

- G1 快速记账：一次记一笔支出或收入，尽量在 10 秒内完成。
- G2 月度总览：清晰展示当月支出、收入、结余、分类占比和每日变化。
- G3 预算控制：设置月度预算，在临近超支时提示用户。
- G4 数据跨设备：账本数据保存在用户自己的 Gitee 私有仓库中，换手机后仍可继续使用。
- G5 数据自主：支持导出、备份和恢复，原始数据归用户所有，不存到第三方服务器。
- G6 跨端基础：核心页面优先满足手机竖屏使用，后续可平滑迁移到微信小程序。

### 1.3 非目标

- 不做投资理财、股票基金等资产管理功能。
- 不做自动抓取微信或支付宝账单的功能。
- v1.1 支持同一账本内的多成员归属和分成员统计，不包含成员独立登录或权限控制。
- v1 不做报销审批、预算审批等企业流程。

## 2. 产品形态与部署建议

用户需要“方便手机使用”，并明确要求数据不能只存在手机上，需要换手机后继续可用。可选形态如下：

| 形态 | 优点 | 缺点 | 适合情况 |
| --- | --- | --- | --- |
| Gitee Pages 前端 + Gitee 私有仓库数据（默认） | 页面和账本数据都在用户自己的 Gitee 账号下，无需额外服务器 | 浏览器直连 Gitee API 存在安全取舍；页面容量和 API 策略受限 | 个人跨手机记账 |
| 移动端网页应用 + 第三方云数据库 | 数据同步体验好，支持后端能力 | 需要额外注册云服务账号 | 愿意使用 Supabase 等免费云服务 |
| 微信小程序 + 微信云开发 | 微信内打开方便，自带云数据库 | 需要注册小程序和 AppID，发布需审核 | 用户明确希望长期在微信中使用 |
| 原生 App | 体验和通知最好 | 开发维护成本最高 | 不是当前阶段最优选择 |

本文默认推荐“Gitee Pages 托管前端 + Gitee 私有仓库保存账本”，原因如下：

- 页面部署和数据存储都放在用户自己的 Gitee 账号下，不新增第三方服务。
- 前端仍是移动端网页应用，任意手机打开同一个网址即可使用。
- 账本以 JSON 文件写入私有仓库，换手机、清浏览器后数据不丢失。
- 页面、交互和统计数据模型按微信小程序的要求设计，后续要迁移小程序时可以复用。

需要特别说明：Gitee Pages 只能托管静态前端页面，不能运行数据库或后端代码。因此本方案让浏览器直接通过 Gitee Open API 读写一个私有仓库中的 JSON 数据文件，本地浏览器只做缓存。

如果最终确定做微信小程序，核心记账需求基本不变，主要变化在“登录方式、云数据库、消息提醒方式和发布流程”。

### 3.2 v1 核心范围说明

v1 先解决“个人记账 + 多手机同步”闭环：

- 用户可以新增、编辑、删除支出和收入。
- 用户可以按天查看明细，按月查看汇总。
- 用户可以设置总预算或分类预算。
- 账本数据自动保存到用户的 Gitee 私有仓库，任意手机打开同一页面都能读取最新数据。
- 用户可以导出 CSV，用于 Excel 复盘或迁移。

应用自身不注册账号；首次使用需要填写 Gitee 用户名和私有访问令牌。令牌只保存在使用者的浏览器本地，不写入代码，也不提交到仓库。

## 4. 用户与典型场景

### 4.1 目标用户

| 用户类型 | 使用习惯 | 核心诉求 |
| --- | --- | --- |
| 上班族 | 每天消费 1-5 次，时间碎片化 | 随手记录，月底复盘支出结构 |
| 居家用户/小型家庭 | 管理日常伙食、水电、购物预算 | 设置月预算，控制超支 |
| 兼职或自由职业者 | 收入和支出不固定 | 记录多笔小额收入，了解每月结余 |

### 4.2 典型场景

#### 场景 1：快速记一笔

1. 小李在便利店买早餐，花费 8.5 元。
2. 打开应用，点击首页的“记一笔”。
3. 系统默认记录类型为支出、日期为今天。
4. 输入金额 8.5，选择分类“餐饮”，点击保存。
5. 首页的本月支出、分类统计和今日明细立即更新。

预期结果：从打开应用到保存完成不超过 10 秒。

#### 场景 2：月末复盘

1. 小王想看看本月钱花在哪里。
2. 打开应用，首页显示本月支出、收入、结余和预算进度。
3. 点击“统计”，查看分类占比、每日趋势和与上月的对比。
4. 发现餐饮支出过高，调整下月预算。

#### 场景 3：补录前一天记录

1. 用户忘记记录昨天的打车费。
2. 点击“记一笔”，将日期改为昨天。
3. 保存后，昨天的明细和本月统计都同步更新。

#### 场景 4：换手机后继续使用

1. 用户在旧手机上正常记账，账本数据已自动写入 Gitee 私有仓库。
2. 用户更换新手机或清空浏览器缓存。
3. 打开应用页面，在设置中填写同一 Gitee 用户名和私有访问令牌。
4. 应用从私有仓库拉取数据，旧记录、分类、账户和预算全部恢复。
5. 继续记账，新记录同样写入同一个仓库。

## 6. 页面与交互

### 6.1 导航结构

移动端采用底部 Tab 导航，保持单手可操作：

| Tab | 页面 |
| --- | --- |
| 首页 | 本月汇总、预算进度、最近记录 |
| 明细 | 按日分组的记录列表 |
| 记一笔 | 中间加号按钮，唤起新增页 |
| 统计 | 月度和历史统计图表 |
| 我的 | 账户、分类、预算、数据导出、设置 |

“记一笔”在手机端建议使用半屏或全屏弹层，默认焦点在金额输入框。

### 6.2 核心交互流程

#### 新增支出流程

1. 点击底部或首页“记一笔”。
2. 选择类型：支出 / 收入。
3. 输入金额。
4. 选择分类。
5. 检查或修改日期、账户、备注。
6. 点击保存。
7. 返回原页面并刷新统计。

#### 查看月度统计流程

1. 点击“统计”Tab。
2. 默认展示当前月份。
3. 左右滑动或点击月份选择器切换月份。
4. 查看汇总、分类占比和趋势图。
5. 点击分类可跳转到该分类当月明细。

### 6.3 交互要求

- 底部主操作按钮位置稳定，不发生位移。
- 金额键盘为纯数字键盘。
- 删除、清空等破坏性操作必须二次确认。
- 空列表、无预算、无分类等状态要有明确引导。
- 日期切换、筛选和保存操作完成后，界面立即反馈。

## 7. 数据与系统要求

### 7.1 基础假设

- 默认币种：人民币 CNY，金额以元显示，内部建议以“分”存储以避免浮点误差。
- 默认时区：Asia/Shanghai，记账日期按本地自然日计算。
- 月份：按公历自然月，例如 2026-09-01 至 2026-09-30。
- 删除：v1 可物理删除；若后续需要统计口径回溯，再改为软删除。

### 7.3 数据一致性

- 分类或账户被停用后，历史记录中的分类和账户信息仍应保留。
- 分类或账户被删除时，若有历史记录，应提示用户先迁移或改用停用方式。
- 同一账本内的支出、收入、预算都按自然月聚合，跨月修改记录时应更新目标月份和原月份的统计，不保留重复聚合结果。

## 9. 验收场景

### 验收 1：新增一笔记录

1. 在首页点击“记一笔”。
2. 输入金额 8.5，选择分类“餐饮”，点击保存。
3. 首页本月支出增加 8.5，最近记录中出现该笔，明细页按今天分组可见。

### 验收 2：修改和删除

1. 打开上一笔记录，把金额改为 10，保存。
2. 首页和统计立即按新金额更新。
3. 删除该记录后，首页和统计恢复删除前金额。

### 验收 3：预算提醒

1. 设置 9 月总预算 2000 元。
2. 当本月支出达到或超过预算的 80% 时，首页展示接近超支提示。
3. 支出超过 2000 元时，展示超支金额，不影响继续记账。

### 验收 4：跨月统计

1. 在 9 月 1 日新增记录，再把日期改到 8 月 31 日并保存。
2. 8 月和 9 月的统计均正确，不出现重复或负数。

### 验收 5：导出

1. 导出 9 月记录为 CSV。
2. 文件包含当月全部支出和收入，字段完整，Excel 打开无乱码。
